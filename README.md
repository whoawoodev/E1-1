# E1-1 · CLI 개발 환경 구축과 Docker 컨테이너 워크플로우

CLI 환경에서 터미널과 Docker의 핵심 기능을 익히고, Git/GitHub과 연동하여 코드 관리부터 컨테이너 실행까지의 전 과정을 실습한다.

- **목표** — 로컬 환경에 의존하지 않고 누구나 같은 방식으로 실행·검증할 수 있는 개발 환경을 손으로 구성한다.
- **수행 흐름** — 터미널로 작업 디렉토리·권한 정리 → Docker 점검 및 컨테이너 운영 → Dockerfile로 커스텀 이미지 제작 → 포트 매핑으로 접속 확인 → 바인드 마운트·볼륨으로 변경 반영과 데이터 영속성 검증 → Git 설정 및 GitHub 연동

<br>

수행 로그를 항목별 파일로 분리했다. 실행 결과를 잘라내지 않고 그대로 남기기 위해서다. `docker info`처럼 출력이 100줄에 가까운 명령도 있어, 한 문서에 모으면 어느 항목을 수행했는지 확인하기 어려워진다. 이 README는 목차 역할만 하고, 실제 증거는 각 문서에 있다.

## II. 실행 환경

| 항목 | 값 |

| OS | macOS 15.7.4 |
| Shell | zsh |
| 컨테이너 런타임 | OrbStack |
| Docker | 28.5.2 |
| Git | 2.53.0 |

> 학습장 iMac은 `sudo` 권한이 제한되어 Docker Desktop을 직접 설치할 수 없다. OrbStack은 관리자 권한 없이 컨테이너를 실행·관리할 수 있고, 실행 시 Docker 엔진이 함께 구동되어 터미널에서 `docker` 명령을 그대로 사용할 수 있다.

## V. 핵심 기술 원리

| 질문 | 관련 문서 | 답변 |
| --- | --- | --- |
| 이미지와 컨테이너의 차이를 빌드/실행/변경 관점에서 구분하면? | [03](docs/03-docker.md), [04](docs/04-dockerfile.md) | 이미지는 읽기 전용 템플릿이고, 컨테이너는 그 위에 쓰기 가능한 레이어를 얹어 실행한 상태다. **빌드** 시점에 `COPY index.html`이 수행되어 콘텐츠가 이미지 안에 굳고, 이후 이미지는 변하지 않는다. **실행** 시에는 이미지 하나로 컨테이너를 여러 개 만들 수 있다(05에서 `web-8080`, `web-8081`을 같은 `my-nginx:1.0`으로 실행). **변경**은 방향이 다르다. 이미지 내용을 바꾸려면 파일을 고치고 다시 빌드해야 하고, 컨테이너 안에서 생긴 변경은 컨테이너를 지우면 함께 사라진다. 07에서 `con1`을 삭제한 뒤에도 파일이 남은 것은 그 데이터가 컨테이너가 아니라 볼륨에 있었기 때문이다. |
| 컨테이너 내부 포트로 직접 접속할 수 없는 이유와, 매핑이 필요한 이유는? | [05](docs/05-port.md) | 컨테이너는 호스트와 분리된 자체 네트워크 네임스페이스를 가지며 별도의 IP를 쓴다. 따라서 호스트에서 `localhost:80`으로 접속하면 그것은 호스트의 80번 포트이지 컨테이너의 80번이 아니고, 컨테이너 네트워크는 외부에서 바로 보이지 않는다. `-p 8080:80`은 호스트 8080으로 들어온 요청을 컨테이너 80으로 전달하는 통로를 여는 설정이다. 이 격리는 제약이자 이점이기도 하다. 05에서 두 컨테이너가 모두 내부적으로 80번을 쓰지만 네트워크가 분리되어 있어 충돌 없이 호스트의 8080과 8081로 나뉘어 접속된다. 호스트에서 웹 서버 두 개를 직접 띄웠다면 80번 포트 충돌로 두 번째는 실행되지 않았을 것이다. |
| 절대 경로와 상대 경로는 어떤 상황에서 각각 선택하는가? | [06](docs/06-bind-mount.md) | 절대 경로는 `/`에서 시작해 현재 위치와 무관하게 같은 대상을 가리키고, 상대 경로는 현재 작업 디렉토리를 기준으로 해석된다. **절대 경로**는 실행 위치가 달라져도 같은 곳을 가리켜야 할 때 쓴다. 06의 바인드 마운트가 그 예로, `-v`의 호스트 쪽 경로는 절대 경로를 요구하므로 `$(pwd)/bind-html`로 현재 위치를 절대 경로로 펼쳐서 전달했다. **상대 경로**는 대상이 프로젝트와 함께 움직일 때 쓴다. 이 README가 `docs/05-port.md`로 링크하는 방식이 그것으로, 절대 경로였다면 저장소를 다른 위치에 클론한 순간 모두 깨진다. Dockerfile의 `COPY index.html`도 빌드 컨텍스트 기준 상대 경로라 폴더째 옮겨도 그대로 빌드된다. 기준은 그 경로가 기계를 옮겨도 유효해야 하는지, 프로젝트를 따라다녀야 하는지다. |
| 파일 권한 숫자 표기(755, 644)는 어떤 규칙으로 결정되는가? | [02](docs/02-permission.md) | 세 자리는 각각 소유자, 그룹, 그 외 사용자를 뜻하고 각 자리는 `r=4`, `w=2`, `x=1`의 합으로 정해진다. `755`는 `rwxr-xr-x`(7=4+2+1, 5=4+1)이고 `644`는 `rw-r--r--`(6=4+2, 4=4)이다. 여기서 디렉토리의 `x`는 실행이 아니라 진입(`cd`)과 내부 접근을 뜻한다는 점이 파일과 다르다. 02 실습에서 `chmod 600`(`rw-------`)으로 바꾼 뒤 `cd`가 막힌 것이 그 때문이며, 읽기와 쓰기 권한은 있었지만 `x`가 없어 진입할 수 없었다. 권한을 되돌리자 다시 들어갈 수 있었다. 디렉토리는 755, 일반 파일은 644를 관례로 쓰는 이유도 같다. 디렉토리는 진입해야 하므로 `x`가 필요하고, 실행 파일이 아닌 일반 파일에는 `x`가 필요 없다. |
