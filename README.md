# E1-1 · CLI 개발 환경 구축과 Docker 컨테이너 워크플로우

CLI 환경에서 터미널과 Docker의 핵심 기능을 익히고, Git/GitHub과 연동하여 코드 관리부터 컨테이너 실행까지의 전 과정을 실습한다.

- **목표** — 로컬 환경에 의존하지 않고 누구나 같은 방식으로 실행·검증할 수 있는 개발 환경을 손으로 구성한다.
- **수행 흐름** — 터미널로 작업 디렉토리·권한 정리 → Docker 점검 및 컨테이너 운영 → Dockerfile로 커스텀 이미지 제작 → 포트 매핑으로 접속 확인 → 바인드 마운트·볼륨으로 변경 반영과 데이터 영속성 검증 → Git 설정 및 GitHub 연동

## V. 핵심 기술 원리

### 이미지와 컨테이너의 차이를 빌드/실행/변경 관점에서 구분하면?

이미지는 읽기 전용 템플릿이고, 컨테이너는 그 위에 쓰기 가능한 레이어를 얹어 실행한 상태다.

- **빌드** — Dockerfile로 이미지를 만드는 단계. 이 시점에 `COPY`가 수행되어 콘텐츠가 이미지 안에 굳는다.
- **실행** — 이미지 하나로 컨테이너를 여러 개 만들 수 있다. 05에서 `web-8080`과 `web-8081`을 같은 `my-nginx:1.0`으로 실행했다.
- **변경** — 이미지 내용을 바꾸려면 다시 빌드해야 하고, 컨테이너 안에서 생긴 변경은 컨테이너를 지우면 함께 사라진다.

> 관련 문서 : [03. Docker 워크플로우](docs/03-docker.md) · [04. Dockerfile](docs/04-dockerfile.md)

### 컨테이너 내부 포트로 직접 접속할 수 없는 이유와, 매핑이 필요한 이유는?

컨테이너는 호스트와 분리된 자체 네트워크 네임스페이스를 쓴다. 호스트에서 `localhost:80`으로 접속하면 그것은 호스트의 80번 포트이지 컨테이너의 80번이 아니며, 컨테이너 네트워크는 밖에서 바로 보이지 않는다. `-p 8080:80`은 호스트 8080으로 들어온 요청을 컨테이너 80으로 전달하는 통로를 여는 설정이다.

이 격리는 제약이자 이점이기도 하다. 05에서 두 컨테이너가 모두 내부적으로 80번을 쓰지만 서로 네트워크가 분리되어 있어 충돌 없이 호스트의 8080과 8081로 나뉘어 접속된다.

> 관련 문서 : [05. 포트 매핑](docs/05-port.md)

### 절대 경로와 상대 경로는 어떤 상황에서 각각 선택하는가?

절대 경로는 `/`에서 시작해 현재 위치와 무관하게 같은 대상을 가리키고, 상대 경로는 현재 작업 디렉토리를 기준으로 해석된다.

- **절대 경로** — 실행 위치가 달라져도 같은 곳을 가리켜야 할 때. 06의 바인드 마운트가 그 예로, `-v`의 호스트 쪽 경로는 절대 경로를 요구하므로 `$(pwd)/bind-html`로 펼쳐서 전달했다.
- **상대 경로** — 대상이 프로젝트와 함께 움직일 때. 이 README가 `docs/05-port.md`로 링크하는 방식이 그것으로, 절대 경로였다면 저장소를 다른 위치에 클론한 순간 모두 깨진다.

> 관련 문서 : [06. 바인드 마운트](docs/06-bind-mount.md)

### 파일 권한 숫자 표기(755, 644)는 어떤 규칙으로 결정되는가?

세 자리는 각각 소유자, 그룹, 그 외 사용자를 뜻하고, 각 자리는 `r=4` `w=2` `x=1`의 합으로 정해진다.

| 숫자 | 조합 | 기호 |
| --- | --- | --- |
| 7 | 4+2+1 | `rwx` |
| 6 | 4+2 | `rw-` |
| 5 | 4+1 | `r-x` |
| 4 | 4 | `r--` |

따라서 `755`는 `rwxr-xr-x`, `644`는 `rw-r--r--`가 된다.

여기서 디렉토리의 `x`는 실행이 아니라 **진입(`cd`)과 내부 접근**을 뜻한다는 점이 파일과 다르다. 02 실습에서 `chmod 600`(`rw-------`)으로 바꾼 뒤 `cd`가 막힌 것이 그 때문이며, 읽기와 쓰기 권한은 있었지만 `x`가 없어 진입할 수 없었다. 디렉토리는 755, 일반 파일은 644를 관례로 쓰는 이유도 같다.

> 관련 문서 : [02. 권한](docs/02-permission.md)

## VI. 심층 인터뷰

### 호스트 포트가 이미 사용 중이라 포트 매핑이 실패한다면, 어떤 순서로 원인을 진단하는가?

충돌은 항상 호스트 쪽 포트에서 생기므로 그 위치부터 좁혀 나간다.

1. 에러 메시지에서 실패한 호스트 포트 번호를 확인한다.
2. `docker ps`로 그 포트를 이미 매핑한 컨테이너가 있는지 본다.
3. 없다면 도커 밖의 프로세스가 점유한 것이므로 `lsof -i :8080`으로 확인한다.
4. 점유 중인 쪽을 정리하거나(`docker rm -f`), `-p 8081:80`처럼 호스트 포트만 바꿔 매핑한다.

컨테이너 내부 포트는 격리되어 있어 그대로 두어도 된다. 바꿔야 하는 것은 언제나 `-p`의 왼쪽이다.

> 관련 문서 : [05. 포트 매핑](docs/05-port.md)

### 컨테이너 삭제 후 데이터가 사라지는 것을 방지하려면 어떤 대안이 있는가?

데이터를 컨테이너의 쓰기 레이어에 두면 수명이 컨테이너와 같아진다. 저장 위치를 컨테이너 밖으로 빼는 것이 대안이다.

- **볼륨** — 도커가 관리하는 저장소에 둔다. 07에서 `con1`을 삭제한 뒤 `con2`로 같은 볼륨을 다시 마운트했을 때 파일이 그대로 남은 것이 이에 해당한다.
- **바인드 마운트** — 호스트 디렉토리를 직접 연결한다. 호스트에서 파일을 함께 편집해야 할 때 쓴다(06).
- **이미지에 포함** — 변하지 않는 콘텐츠라면 `COPY`로 빌드 시점에 넣는다.

컨테이너만 쓰는 데이터는 볼륨, 호스트와 공유해야 하면 바인드 마운트를 고른다. 볼륨은 호스트 경로에 묶이지 않아 다른 기계에서도 같은 명령이 동작하고, 권한 초기화를 도커가 처리한다는 이점도 있다.

> 관련 문서 : [07. 볼륨 영속성](docs/07-volume.md)
