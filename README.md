# E1-1 · CLI 개발 환경 구축과 Docker 컨테이너 워크플로우

CLI 환경에서 터미널과 Docker의 핵심 기능을 익히고, Git/GitHub과 연동하여 코드 관리부터 컨테이너 실행까지의 전 과정을 실습한다.

- **목표** — 로컬 환경에 의존하지 않고 누구나 같은 방식으로 실행·검증할 수 있는 개발 환경을 손으로 구성한다.
- **수행 흐름** — 터미널로 작업 디렉토리·권한 정리 → Docker 점검 및 컨테이너 운영 → Dockerfile로 커스텀 이미지 제작 → 포트 매핑으로 접속 확인 → 바인드 마운트·볼륨으로 변경 반영과 데이터 영속성 검증 → Git 설정 및 GitHub 연동

<br>

```

├── README.md                  # 수행 항목 요약과 문서 링크
├── docs/                      # 항목별 수행 로그 (명령어 + 실행 결과)

│   ├── 02-permission.md

│   ├── 07-volume.md
│   └── 08-git-github.md

└── troubleshooting/           # 실습 중 발생한 문제와 해결 과정
```

수행 로그를 항목별 파일로 분리했다. 실행 결과를 잘라내지 않고 그대로 남기기 위해서다. `docker info`처럼 출력이 100줄에 가까운 명령도 있어, 한 문서에 모으면 어느 항목을 수행했는지 확인하기 어려워진다. 이 README는 목차 역할만 하고, 실제 증거는 각 문서에 있다.

<br>

## II. 실행 환경

| 항목 | 값 |
| --- | --- |
| OS | macOS 15.7.4 |
| Shell | zsh |
| 컨테이너 런타임 | OrbStack |
| Docker | 28.5.2 |
| Git | 2.53.0 |

> 학습장 iMac은 `sudo` 권한이 제한되어 Docker Desktop을 직접 설치할 수 없다. OrbStack은 관리자 권한 없이 컨테이너를 실행·관리할 수 있고, 실행 시 Docker 엔진이 함께 구동되어 터미널에서 `docker` 명령을 그대로 사용할 수 있다.

## V. 핵심 기술 원리

| 질문 | 관련 문서 | 답변 |
| --- | --- | --- |
| 이미지와 컨테이너의 차이를 빌드/실행/변경 관점에서 구분하면? | [03](docs/03-docker.md), [04](docs/04-dockerfile.md) | 이미지는 읽기 전용 템플릿, 컨테이너는 그 위에 쓰기 레이어를 얹어 실행한 상태다. 빌드 시점에 콘텐츠가 이미지에 굳고, 같은 이미지로 컨테이너를 여러 개 만들 수 있다(05). 이미지를 바꾸려면 재빌드해야 하고, 컨테이너 안의 변경은 삭제하면 사라진다. |
| 컨테이너 내부 포트로 직접 접속할 수 없는 이유와, 매핑이 필요한 이유는? | [05](docs/05-port.md) | 컨테이너는 호스트와 분리된 네트워크 네임스페이스를 써서 밖에서 바로 보이지 않는다. `-p 8080:80`이 호스트 8080을 컨테이너 80으로 잇는 통로다. 이 격리 덕분에 05에서 두 컨테이너가 모두 내부 80을 쓰면서도 충돌 없이 8080과 8081로 나뉜다. |
| 절대 경로와 상대 경로는 어떤 상황에서 각각 선택하는가? | [06](docs/06-bind-mount.md) | 절대 경로는 현재 위치와 무관하게 같은 곳을, 상대 경로는 현재 디렉토리를 기준으로 가리킨다. 바인드 마운트는 절대 경로를 요구해서 `$(pwd)/bind-html`로 넘겼고, 반대로 이 README의 문서 링크는 저장소를 어디에 클론해도 유지되도록 상대 경로로 썼다. |
| 파일 권한 숫자 표기(755, 644)는 어떤 규칙으로 결정되는가? | [02](docs/02-permission.md) | 세 자리는 소유자·그룹·그 외를 뜻하고 각 자리는 `r=4`, `w=2`, `x=1`의 합이다. `755`는 `rwxr-xr-x`, `644`는 `rw-r--r--`가 된다. 디렉토리의 `x`는 실행이 아니라 진입 권한이라, 02에서 `chmod 600` 후 `cd`가 막힌 것이 그 때문이다. |

## VI. 심층 인터뷰

| 질문 | 관련 문서 | 답변 |
| --- | --- | --- |
| 호스트 포트가 이미 사용 중이라 포트 매핑이 실패한다면, 어떤 순서로 원인을 진단하는가? | [05](docs/05-port.md) | 충돌은 항상 호스트 쪽 포트에서 생기므로 그 위치부터 좁혀 나간다. ① 에러 메시지에서 실패한 호스트 포트 번호를 확인한다. ② `docker ps`로 그 포트를 이미 매핑한 컨테이너가 있는지 본다. ③ 없으면 도커 밖의 프로세스가 점유한 것이므로 `lsof -i :8080`으로 확인한다. ④ 조치는 점유 중인 쪽을 정리하거나(`docker rm -f`), `-p 8081:80`처럼 호스트 포트만 바꿔 매핑한다. 컨테이너 내부 포트는 격리되어 있어 그대로 두어도 된다. |
| 컨테이너 삭제 후 데이터가 사라지는 것을 방지하려면 어떤 대안이 있는가? | [07](docs/07-volume.md) | 데이터를 컨테이너의 쓰기 레이어에 두면 수명이 컨테이너와 같아지므로, 저장 위치를 컨테이너 밖으로 빼는 것이 대안이다. ① **볼륨** — 도커가 관리하는 저장소에 두는 방식으로, 07에서 `con1`을 삭제한 뒤 `con2`로 다시 마운트했을 때 파일이 그대로 남은 것이 이에 해당한다. ② **바인드 마운트** — 호스트 디렉토리를 직접 연결하는 방식으로, 호스트에서 파일을 함께 편집해야 할 때 쓴다(06). ③ 변하지 않는 콘텐츠라면 `COPY`로 이미지에 포함시킨다. 컨테이너만 쓰는 데이터는 볼륨, 호스트와 공유해야 하면 바인드 마운트를 고른다. |
| 이 미션에서 가장 어려웠던 지점과 해결 과정(가설 → 확인 → 조치)은? | [트러블슈팅](troubleshooting/) | |
